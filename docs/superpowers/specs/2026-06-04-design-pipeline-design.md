# design-pipeline — дизайн-надстройка над superpowers

**Дата:** 2026-06-04
**Автор:** Анатоль + Claude
**Статус:** design approved, переход к плану реализации

## Проблема

superpowers силён в процессе (brainstorm → PRD → оркестрация агентов → разработка),
но когда агенты доходят до генерации UI, результат стабильно «так себе».
Подтверждённые боли (болят все четыре сразу):

1. **Визуал/эстетика** — типографика, цвет, отступы, композиция выглядят дёшево,
   generic, «AI slop», без характера.
2. **UX/структура** — навигация, иерархия, флоу не продуманы; путь пользователя слабый.
3. **Нет докрутки** — агент не смотрит на результат глазами и не итерирует; сдаёт
   с первого слепого захода.
4. **Нет единого стиля** — каждый экран/компонент в своём стиле, нет дизайн-системы,
   экраны разъезжаются между собой.

## Цель / success criteria

UI на выходе superpowers не стыдно показать: целостный по стилю, с продуманным UX,
с не-generic эстетикой, и докрученный по реальному виду в браузере — а не сданный вслепую.

## Не-цели (YAGNI)

- **НЕ** многоагентный adversarial design-review с пачкой критиков и голосованием
  (Подход 3 был отклонён как оверкилл для лендингов — можно нарастить позже).
- **НЕ** трогаем backend/логику — скилл занимается только UI/UX.
- **НЕ** завязка на конкретный стек (Tailwind config и т.п.) — решение стек-агностичное.

## Архитектура

Новый скилл **`design-pipeline`** в `~/Work/claude-config/skills/design-pipeline/SKILL.md`
(глобально, симлинком в `~/.claude/skills/`, как остальные скиллы Анатоля).

**Триггеринг — два пути:**
1. Явный вызов: «сделай дизайн», «design», «прокачай UI».
2. Правило в `CLAUDE.md`: когда агенты superpowers доходят до генерации UI — обязаны
   вызвать `design-pipeline`, а не лепить вслепую.

**Стек-агностичность:** базис дизайн-системы — CSS custom properties (`tokens.css`),
работают в любом стеке. Для Tailwind/CSS-in-JS токены маппятся, но источник правды — CSS-переменные.

## Фазы pipeline

Каждая фаза бьёт по своей боли. Для мелких задач можно вызвать отдельную фазу
(например только фазу 3 — review), не гоняя весь pipeline.

### Фаза 0 — UX
- **Вход:** PRD / идея из brainstorm.
- **Инструмент:** существующий скилл `ux-discovery` (скилл Анатоля).
- **Делает:** разбирает структуру, user journey, happy path, точки трения.
- **Артефакт:** `ux-brief.md`.
- **Лечит:** UX/структура.

### Фаза 1 — Design System
- **Вход:** `ux-brief.md` + контекст проекта (бренд, тон).
- **Делает:** генерит дизайн-систему **один раз на проект** (переиспользуется всеми экранами):
  типографическая шкала, цветовая система, spacing, радиусы, тени, motion-принципы.
- **Артефакт:** `design-system.md` (человекочитаемая спека) + `tokens.css` (CSS-переменные).
- **Лечит:** единый стиль.

### Фаза 2 — Build
- **Вход:** `ux-brief.md` + `design-system.md` + `tokens.css`.
- **Инструмент:** плагин `frontend-design` (Anthropic) активен при генерации.
- **Делает:** агенты генерят UI, **обязаны** опираться на `tokens.css` и соблюдать
  дизайн-систему; frontend-design гонит не-generic эстетику.
- **Артефакт:** код UI.
- **Лечит:** визуал/эстетика.

### Фаза 3 — Visual Review
- **Вход:** собранный UI (dev-server / статика).
- **Инструмент:** плагин `superpowers-chrome` (Chrome DevTools, настоящие скриншоты).
- **Делает:** открывает результат → **делает скриншот** → агент СМОТРИТ глазами →
  сверяет с `design-system.md` и UX-чеклистом → формирует правки → докручивает в цикле,
  пока не сойдётся (с разумным лимитом итераций, чтобы не жечь токены бесконечно).
- **Артефакт:** отчёт о найденном + применённые правки.
- **Лечит:** докрутка.

## Data flow

```
PRD ──▶ [Фаза 0: ux-discovery] ──▶ ux-brief.md
                                        │
                                        ▼
            [Фаза 1: design system] ──▶ design-system.md + tokens.css
                                        │
                                        ▼
   ux-brief + tokens ──▶ [Фаза 2: frontend-design] ──▶ код UI
                                        │
                                        ▼
            [Фаза 3: chrome review] ──▶ скриншот → сверка → правки ──┐
                                        ▲                            │
                                        └──── цикл докрутки ─────────┘
```

## Зависимости

| Компонент | Действие | Источник |
|---|---|---|
| `ux-discovery` | уже есть | claude-config/skills (Анатоль) |
| `frontend-design` | включить плагин | claude-plugins-official (Anthropic) |
| `superpowers-chrome` | включить плагин | superpowers-marketplace (obra) |

Включение в `settings.json` → `enabledPlugins`:
- `"frontend-design@claude-plugins-official": true`
- `"superpowers-chrome@superpowers-marketplace": true`

(Маркетплейс obra остаётся в `extraKnownMarketplaces`; плагин chrome включается
независимо от отключённого `superpowers@superpowers-marketplace`.)

## Граничные случаи

- **Backend/логика** — скилл не вмешивается, только UI/UX.
- **Мелкий фикс** — можно вызвать одну фазу (например только review), не весь pipeline.
- **Лимит итераций фазы 3** — фиксированный потолок докруток, чтобы цикл не жёг токены.
- **Нет dev-server** — для статики chrome открывает файл напрямую; для SPA нужен
  запущенный dev-server (фаза 3 проверяет/подсказывает).

## Решения и обоснования

- **Инструмент скриншотов = superpowers-chrome**, не Playwright MCP (у Анатоля
  freeze bug после скриншотов) и не agent-browser (отдаёт ref-дерево, а не картинку —
  не годится для оценки эстетики).
- **Дизайн-система отдельной фазой**, а не на каждом экране — иначе экраны разъезжаются.
- **Стек-агностичный базис = CSS-переменные**, потому что стек у Анатоля разный под проект.
